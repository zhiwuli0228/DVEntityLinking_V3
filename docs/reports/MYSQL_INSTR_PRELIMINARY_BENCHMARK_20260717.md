# MySQL `INSTR` 实体词召回预压测报告

## 1. 结论

当前 `MATCH_WORDS` 反向包含查询不具备直接作为生产容量基线的条件。在远程 MySQL、约 9.57 万 active entity word 下：

- 并发 1 的整体 P95 为 2.42 秒；并发 10 的 P95 为 15.65 秒，并出现 5/60 次连接类错误；并发 25 的 P95 为 26.32 秒，并出现 3/75 次连接类错误。
- 长 Query 是最明显的 CPU/字符串扫描放大场景：并发 10、25 的 P95 分别为 16.26 秒和 28.71 秒。
- 无类型过滤时，`EXPLAIN ANALYZE` 实际扫描全部 95,653 条 active 词，数据库内执行约 290 毫秒；增加 `device` 类型过滤后只扫描 4,782 条，数据库内执行约 10.9 毫秒。
- 客户端单次调用仍存在约 450 毫秒的远程链路底噪，说明数据库扫描和远程链路都需要分别治理。

本次是有边界的预压测，不是正式上线容量验收。由于尚未确认 P4 延迟预算、目标 QPS 和错误率 SLO，不能据此给出正式 `N_max`。但 5 万词条后并发 10/25 的尾延迟已明显恶化，足以判定当前实现必须继续优化并进入专用环境正式压测。

## 3. 数据与 Query 分布

- entity type：`metric` 80%，`alarm/application/device/service` 各 5%。
- source：`entity_name` 约 1/3，`alias` 约 2/3。
- normalized key：短编码、普通业务名、结构化告警编码、长服务指标名四类混合。
- Query：无匹配、唯一命中、多实体命中、重复命中、约 1 KiB 长 Query、`device` 类型过滤六类循环执行。
- 每次查询均读取完整 `MATCH_WORDS` 返回列并消费结果集；连接在一轮并发测试内保持复用。

## 5. 执行计划

无类型过滤：

```text
access_type: ref
key: idx_status_entity_type
optimizer rows_examined_per_scan: 48,372
actual index rows: 95,653
actual total database time: 290.356 ms
result rows: 0
```

`device` 类型过滤：

```text
access_type: ref
key: idx_status_entity_type
optimizer rows_examined_per_scan: 8,604
actual index rows: 4,782
actual total database time: 10.909 ms
result rows: 1
```

`status/entity_type` B-Tree 可以缩小前置集合，但不能直接优化 `INSTR(:normalized_query, normalized_key)`。无类型过滤时仍需对全部 active 词执行字符串判断；类型过滤使本次数据库内执行时间下降约 26.6 倍。

## 6. 测试过程异常与工具修正

首轮完成 1 万、5 万档后，控制连接在进入 10 万档时收到 MySQL 2013 断连。原连接无法执行 `finally` 清理，测试程序随后使用精确 schema 名重新连接并清理成功。脚本已补充以下保护：

- 建数、执行计划和清理前主动检查并重连控制连接。
- 原连接清理失败时重新建立管理连接，只允许删除符合严格正则的本轮 `dv_el_perf_*` schema。
- 后续运行只记录异常类型与数值错误码，不保存连接信息、凭据或完整服务端消息。

修正后 10 万档完成，自动清理成功。最终通过 `INFORMATION_SCHEMA` 对两轮精确 schema 名进行检查，残留为 0。

## 7. 风险判定与后续门禁

1. `INSTR` 当前呈明显的数据量与并发放大，5 万词条已出现吞吐下降和长 Query 尾延迟跃升。
2. `entity_types` 必须尽可能由调用策略收窄，但它只能缓解特定查询，不能替代召回索引结构优化。
3. 远程调用必须使用长期连接池，并单独设定连接、读取和总调用预算；当前公网链路不适合作为生产低延迟结论。
4. 应在 `DVAIAgentService` 内评估 n-gram/前缀桶倒排投影或专用检索索引，保持 `MATCH_WORDS` 请求和响应契约不变，再使用相同 golden query 集复测正确性和性能。
5. 正式上线前必须补齐 50/100 并发、50 万至生产峰值 1.5 倍数据、至少 15 分钟持续压测、真实接口与 Query Recall 端到端、发布并发、CPU/I/O/锁/连接池指标。
6. 只有在明确 P4 P95 预算和目标并发后，才能计算 `N_max`；预计生产峰值不得超过 `0.6 × N_max`。

因此，设计文档中的 `INSTR` 专项性能验收项继续保持未完成状态，本报告仅作为优化前基线和容量风险证据。
