## Context

V4 已冻结为只读实体链接 module：它通过 Entity Data IR 读取实体词与实体详情，且 V4.1 禁止默认运行链使用历史资产。V5 在此边界之外以独立 Entity Build Plugin 提供实体写入侧：从运行时接口和知识库接口取数、构建 V4 schema 实体、批量发布至 Entity Data Service，并在宿主显式装配后执行启动及每日凌晨刷新。V4 与 V5 共同复用独立常驻的 REST 请求工具，但不彼此导入。

调用者目前会自行处理远程访问细节，导致 URL、认证、重试、超时和错误语义分散。V5 需要将 HTTP 协议处理集中在一个工具中，同时不让业务类感知具体 HTTP client 或请求执行细节。

## Goals / Non-Goals

**Goals:**

- 在来源、版本与诊断可追踪的前提下构建 canonical entity，并以批量、幂等的方式发布。
- 让所有远程交互经单一 REST 请求工具执行；业务调用方只声明请求意图与输入。
- 提供启动同步和每天凌晨（默认 `Asia/Shanghai`，可显式配置）的一次刷新，避免同一实例任务重叠。
- 失败时保持上一个已发布数据快照可读，并生成不含凭据或完整 payload 的运行记录；每日刷新不创建新的软件版本。
- 保持既有链接状态、只读 Entity Data IR、确定性回退和 V4.1 隔离规则不变；V5 新对外 DTO 去除版本后缀。
- 保证 V5 构建能力为原子插件，可整体移入 Entity Data Service，不改动 V4。

**Non-Goals:**

- 不让 V5 链接 module 直连数据库或使用历史 JSON、Redis/Gauss Mock 作为默认数据源。
- 不在 V4 module、linking pipeline 或 Web adapter 中导入、实例化或触发 V5 插件。
- 不自动生成未经确认的 alias，不以知识库自由文本覆盖已有 canonical 实体。
- 不在首期定义真实外部 URL、认证凭据、知识库产品适配或分布式多实例调度协调。
- 不以每日任务失败触发删除、清空或未经验证的反向迁移。

## Decisions

### 1. 写入侧以构建管线与发布端口分离

`EntityConstructionService` 编排来源拉取、canonical 映射、校验、去重、冲突拒绝和批量发布；`EntityPublisher` 是写入 Entity Data Service 的端口。构建器不会直接调用 HTTP，也不会直接执行数据库操作。这使来源适配、校验和发布可独立测试，并延续 V4 的 IR 边界。

直接把上游 payload 转发给数据服务被拒绝，因为它无法保证 canonical schema、来源追踪和 fail-closed 冲突语义。

### 1.1 V5 以独立插件而非 V4 子模块装配

`EntityBuildPlugin` 是 V5 组件的唯一装配根，包含构建、来源 adapter、REST 工具、发布端口、刷新协调器和调度器。它只能由宿主显式创建和调用；V4 不持有插件引用，也不调用刷新。V4 继续只读 Entity Data Service。

将构建能力直接加入 V4 module 被拒绝，因为这会把写入、调度和上游可用性风险带入链接运行链，并使后续整体迁移到 Entity Data Service 变得困难。

### 2. 共享 REST 请求由不可泄露的声明式请求对象驱动

V4 与 V5 的业务适配器向独立共享 `RestRequestTool` 提供 `url`、`method`、`params`、`json_body`、安全认证引用、超时策略和可选 idempotency key；工具统一执行请求、认证注入、超时、有限重试、响应解码、错误归一化和安全 trace。业务适配器仅接收结构化成功值或结构化错误，不导入底层 HTTP client 或平台 IR client。V4 现有 `platform_client` 成为工具可注入的 transport，不改变 V4 工厂参数。

让每一个来源 adapter 或 V4 Entity Data adapter 使用自己的 requests/httpx/platform 调用被拒绝，因为会破坏错误一致性、审计和凭据保护。

### 3. 合并以来源优先级与确定性冲突拒绝实现

运行时数据和知识库数据先由 adapter 映射为仅含 V4 既有字段的标准实体，再按稳定实体标识和可配置来源优先级合并；关键字段不一致、实体词归一化冲突或必填字段缺失均拒绝该批次更新。来源类别仅用于 adapter 选择和运行诊断，绝不写入实体。成功报告仅保留计数、结果状态、冲突代码和安全摘要。

“后到数据覆盖先到数据”被拒绝，因为无法解释知识库与运行时数据的优先级，也可能破坏 V4 单值实体词约束。

### 4. 刷新采用启动触发加本进程单飞定时器

服务生命周期显式调用首次 `refresh()`；调度器随后根据明确时区与每日午夜 cron 计算下一次运行。调度器在单实例内使用互斥锁，若上一轮未结束则记录 `refresh_skipped_in_progress` 而不并发发布。候选快照仅在完整构建、验证和对账成功后才原子切换，失败保留最近成功数据快照。

首期不假定分布式锁或特定 scheduler 框架；多实例部署须在宿主层确保仅一个调度 leader，或在后续版本增加分布式协调。

### 5. 数据快照必须以构建标识、对账和幂等键保护

每轮构建仅生成 V4 schema 的完整实体集合和安全运行结果；发布端口完成批量写入对账后原子切换当前数据。重试同一构建不得产生重复实体或删除上一成功数据。每日更新不代表 V5.x 软件版本，也不得向实体加入任何版本、来源、时间或快照字段；软件版本只随代码、契约、schema、构建规则或来源优先级的评审变更演进。调用 Entity Data Service 的真实写接口、认证格式、对账与原子切换能力作为可配置 adapter 契约，不能在无授权环境中猜测实现。

## Risks / Trade-offs

- [上游接口缺少稳定版本或增量游标] → 以安全快照摘要、时间窗和全量对账作为首期回退，并将来源快照标识能力列为接入门禁。
- [知识库文本质量不稳定] → 仅接受通过 schema/来源规则的结构化映射；不自动产生 alias，冲突 fail-closed。
- [单实例锁不能覆盖多副本] → 在部署手册中要求宿主 leader；后续再按真实部署环境引入分布式锁。
- [HTTP 重试可能重复写入] → 仅对明确可重试错误执行有限重试，并使用 idempotency key 与发布批次标识。
- [启动同步延迟影响服务可用性] → 生命周期支持明确的 blocking 或 background 模式；首次实现默认必须在 health/readiness 中暴露同步状态。

## Migration Plan

1. 建立 V5 IR/SR、独立插件边界、V4 schema 构建输入/输出和 REST 请求契约，并冻结 V4 只读边界。
2. 实现 REST 请求工具及其假 client 测试，再实现运行时/知识库来源 adapter 与构建校验。
3. 接入批量发布 stub，验证幂等、冲突拒绝、部分来源失败和安全报告。
4. 接入生命周期和单实例调度，在受控环境验证启动同步、午夜调度、失败保留及重启恢复。
5. 取得外部来源和 Entity Data Service 的授权契约后，执行 dry-run、对账、有限灰度和回退演练。

回退只停止 V5 刷新任务并将 `current` 切回 Entity Data Service 的最近成功数据快照；不得清空数据或执行未经验证的反向写入。该回退不改变软件版本。

## Open Questions

- 运行时数据和知识库的正式接口、认证方式、分页/增量游标及数据 owner 是什么？
- Entity Data Service 的候选快照写入、对账、原子切换、保留和快照回退 API 契约是什么？
- 服务的目标部署形态是单实例、宿主 leader，还是多副本；是否需要分布式锁？
- 启动首次同步应阻塞 readiness，还是后台运行并以 health 状态暴露？
